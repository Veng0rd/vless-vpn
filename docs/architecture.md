# Архитектура

## Почему split routing нельзя сделать только на сервере

Если весь трафик уже ушёл в туннель и приехал на ваш VPS в Нидерландах, то для российских сервисов исходным адресом будет IP VPS, а не ваш домашний адрес. Поэтому правило "российские сервисы напрямую, остальное через VPN" должно срабатывать **до отправки трафика в туннель**:

- либо на самом устройстве
- либо на роутере
- либо в системном TUN-клиенте

Из этого следует архитектура проекта:

- сервер: `3x-ui` + `Xray`, только приём `VLESS TCP Reality`
- клиент: `TUN` + routing rules, где RU-трафик идёт `direct`

## Почему выбран именно этот стек

- `3x-ui` даёт удобное управление inbound-ами и клиентами
- `VLESS TCP Reality` подходит под ваш текущий сценарий без домена
- `runetfreedom` даёт регулярно обновляемые правила и geo-файлы для маршрутизации
- Docker нужен, чтобы запускать всё повторяемо и без ручной раскладки по системе

## Почему домен сейчас не нужен

В текущем проекте нет:

- Cloudflare fronting
- reverse proxy для панели
- ACME/Let's Encrypt

Reality работает поверх публичного IP сервера и SNI сайта-донора, поэтому для базового варианта домен не требуется.

## Какие правила маршрутизации заложены

Основной пользовательский сценарий: `всё кроме РФ через VPN`.

Поэтому в кастомном пресете прямым маршрутом идут:

- `geoip:private`
- `geosite:private`
- `geosite:ru-available-only-inside`
- `geoip:ru`
- доменные зоны `.ru`, `.su`, `.xn--p1ai`

Всё остальное уходит в `proxy`.

## Выбранный donor/SNI по умолчанию

По умолчанию в `.env.example` указан:

- `REALITY_DEST=www.microsoft.com:443`
- `REALITY_SERVER_NAMES=www.microsoft.com,dl.google.com,www.apple.com,gateway.icloud.com`

Это не жёсткое требование. Позже на сервере мы отдельно проверим, какой донор стабильно reachable именно с вашего VPS в Нидерландах.
